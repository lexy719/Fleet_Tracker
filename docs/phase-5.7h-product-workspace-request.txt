FleetOS — Phase 5.7H: Product-Grade Adaptive Workspace, Spatial Composition & Domain Information Architecture
Mission
Phase 5.7G successfully established the semantic interaction layer:
- Anchor
- Active lenses
- Lead lens
- Semantic groups
- Participation contracts
- Guided composition families
- Interaction graph
- Cross-domain transitions
- Selection persistence
- Spatial questions
- Explicit map intent
- Temporary takeover
- Exact Esc/history restoration
These foundations must be preserved.
Do NOT reset the architecture.
However, the current workspace is still visibly a laboratory.
The semantic behavior is improving faster than the actual product experience.
Many states still look:
- visually basic;
- under-dense;
- repetitive;
- too similar across domains;
- dominated by a small number of spatial arrangements;
- overly dependent on HORIZONTAL_JOURNEY;
- correct in camera framing but weak in map-region shape;
- too close to “title + metric + rows + map strip”.
Phase 5.7H must change that.
This is the first phase where proof-of-concept visual quality is no longer acceptable.
The workspace must begin to look and behave like a finished operational product for a professional fleet operator.
1. New acceptance standard
From this phase onward:
passing tests is necessary but not sufficient.
preserving state is necessary but not sufficient.
selecting the correct spatial question is necessary but not sufficient.
the correct camera bounds are necessary but not sufficient.
The UI must also:
- use space intelligently;
- have strong information hierarchy;
- feel specific to the task;
- show realistic operational depth;
- have clear relationships between information;
- look deliberate at first glance.
Strong rule:
Do not confuse architectural correctness with product quality.

4. Interaction Graph scalability
Phase 5.7G defines 30 directed domain pairs across six major domains. This was useful for proving behavior, but it must not become the permanent scaling model.     FleetOS-5.7G-Relatorio-Visual-C…
As FleetOS grows, a complete directed graph becomes too expensive:
6 domains → 30 directed pairs
8 domains → 56
10 domains → 90
12 domains → 132

Refactor the Interaction Graph into:
generic lens contracts
+
semantic-group rules
+
sparse pair-specific overrides

Generic behavior should be derived from:
- source semantic group;
- target semantic group;
- current anchor;
- current lead;
- selected entities;
- relevance.
Only use pair-specific overrides when the relationship genuinely requires special behavior.
Example:
Resources → Assurance

should provide a useful generic relationship.
Driver → Documents may then add Driver-specific content only where necessary.
Strong principle:
The interaction graph should become sparse specialization, not a complete mandatory matrix.
5. Preserve the existing 30 pairs as evidence
Do NOT throw away the existing contracts.
Use them as a behavior dataset.
For each current pair:
classify whether its behavior can be explained by:
- generic group rule;
- generic target-lens rule;
- anchor rule;
- true pair-specific override.
Produce a DEV diagnostic showing:
generic
inherited
overridden

The goal is to prove that future domains do not require N×N manual behavior.
6. Spatial questions must influence map geometry, not only camera
This is one of the most important changes in this phase.
Phase 5.7G correctly made camera framing depend on the spatial question.     FleetOS-5.7G-Relatorio-Visual-C…
Now extend the model.
A spatial question should influence:
camera
+
map-region shape
+
map prominence
+
map position

Strong rule:
The correct camera inside the wrong-shaped map is still the wrong experience.
7. Spatial presentation contracts
Introduce a presentation preference for each spatial question.
Not fixed geometry.
A preferred spatial character.
Example:
CURRENT_ENTITY
Good shapes:
- compact square;
- portrait local map;
- small contextual map.
Usually does NOT need:
- huge route-wide map.
NEXT_LEG
Good shapes:
- medium corridor;
- wide local route;
- supporting horizontal map.
FULL_ROUTE
Often prefers:
- wide landscape region;
- larger route-oriented map;
- potentially dominant spatial region.
Avoid squeezing a long Porto–Madrid route into a narrow portrait map unless layout constraints genuinely require it.
ROUTE_AND_STOP
Often benefits from:
- wide route relationship;
- enough room to show route + station + detour.
AFFECTED_SEGMENT
Often benefits from:
- square/large local area;
- strong road visibility.
MULTI_ENTITY
Often benefits from:
- broad overview map;
- potentially dominant geography.
NONE
Map hidden.
These are design affinities, not hardcoded dimensions.
8. Spatial question may trigger a composition-family variation
Same lead, different spatial question may justify a different physical composition.
Example Driver:
Driver + CURRENT_ENTITY

could use:
compact local map left
+ Driver work area right

while:
Driver + FULL_ROUTE

could use:
Driver area upper/left
+ broad map below

or another authored arrangement.
Do not force all Driver spatial questions into the same map container.
9. Composition families need internal variation
Do NOT solve repetition by adding 12 new families.
Keep the six existing families as conceptual structures.
But allow each family to support authored sub-arrangements.
Example:
HORIZONTAL_JOURNEY
should support different valid arrangements such as:
lead above / map below
map above / lead below
lead + support above / map full width below
map wide center band
map bottom 30%
map bottom 45%
asymmetric lead/support above map

Selection between sub-arrangements must depend on:
- spatial question;
- lead;
- viewport;
- information density;
- number of supporting semantic groups.
Not random.
Strong principle:
A composition family is a language, not one exact layout.
10. HORIZONTAL_JOURNEY repetition must be explicitly reviewed
Phase 5.7G still resolves many states to HORIZONTAL_JOURNEY.
Audit every use of it.
For each state ask:
- Is this family genuinely the best answer?
- Is the map shape appropriate?
- Is another family better?
- Can the same family use a different authored sub-arrangement?
Do NOT change a family only for diversity.
But do not keep it merely because it already exists.
11. Domain-specific information architecture
This phase must significantly deepen the actual domain content.
Current synthetic content is sufficient for architecture testing, but no longer sufficient for visual/product evaluation.
Still use synthetic DEV data.
Do not integrate production repositories yet.
But design each domain as if it will eventually receive real operational data.

21. Information density must respond to gained space
Strong rule:
When a domain gains meaningful space, its information architecture should gain useful depth.
Do not merely increase margins.
Example:

WORKING
LEAD

Success condition
Phase 5.7H succeeds when FleetOS stops looking like a sophisticated interaction laboratory and begins to look like a finished operational product.
Specifically:
- Driver feels like Driver work.
- Truck feels like Truck work.
- Fuel feels like a decision workspace.
- Documents feels like operational documentation.
- Restrictions feels like road-intelligence analysis.
- Jobs remains a strong operational collection.
- cross-domain context still feels continuous.
- selections persist only when relevant.
- map geometry matches the spatial question.
- map camera matches the spatial question.
- composition families no longer look repetitive.
- empty space is intentional.
- added detail is operationally useful.
- no domain becomes generic card soup.
Final principles:
Architectural correctness is necessary, but no longer sufficient.
The correct camera inside the wrong map shape is still wrong.
Spatial semantics must influence both camera and composition.
A composition family is a language, not one fixed layout.
Different operational questions must look operationally different.
When a domain gains space, it should gain useful depth.
Dense where useful. Calm where possible.
No decorative filler. Every element must answer an operational question.
The interaction graph should scale through generic contracts and sparse overrides.
Same product identity, different task character.
If it still looks like a lab screenshot, keep iterating.
